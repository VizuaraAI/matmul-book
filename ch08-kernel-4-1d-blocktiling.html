Chapter 8 · The instruction-starved kernels

Kernel 4: 1D blocktiling

Give each thread eight outputs in a column, and one loaded B value serves all eight. Nine loads for eight multiply-adds, and the lanes start getting fed. We watch it happen, load by load, on the 8 × 8 example.

Kernel · sgemm1DBlocktiling · 8,475 GFLOP/s · 36.5% of cuBLAS · measured by Simon Boehm on an NVIDIA A6000

Chapter 7 left us with a precise target: get below two shared-memory loads per multiply-add. So ask the question that solves it. When can one load serve more than one multiply-add? Only when two multiply-adds want the same number. So look at the definition of the output and find where operands repeat.

C[i][j]  =  sum over k of  A[i][k] × B[k][j]

Take two outputs in the same column, C[i][j] and C[i+1][j]. At step k the first needs A[i][k] × B[k][j] and the second needs A[i+1][k] × B[k][j]. Two different values of A, but the same value of B. Take two outputs in the same row instead, C[i][j] and C[i][j+1], and it is the other way round: the same A value, two different B values. Kernel 3's thread owns one output, so at each step it loads one A and one B and uses each exactly once. Nothing repeats inside a single thread, so nothing can be reused. The way to reuse a loaded value is to give one thread several outputs that want it.

8.1The sharing, seen on the tile

The 8 × 8 example from chapter 4 is exactly the right size for this chapter, because a block of kernel 4 with the tile edge set to 8 has eight threads, each owning one column of eight outputs, and K = 8 makes the chunk the whole matrix. So everything below is the real inner loop of Boehm's kernel, with the same BK = 8 and the same TM = 8 he uses; only the tile edge (8 instead of 64) and the number of chunks (1 instead of 512) are smaller. First, the problem it solves, on kernel 3's version of the same tile.

8.2Kernel 4, every step

Here is Boehm's inner loop, with TM = 8. Each thread keeps eight running totals in registers, one per output of its column. For each value of dotIdx it loads one value of Bs into a register, then walks its eight rows of As, doing one multiply-add per row with that same B value.

float threadResults[TM] = {0.0};          // 8 running totals, in registers

for (uint dotIdx = 0; dotIdx < BK; ++dotIdx) {
  float tmpB = Bs[dotIdx * BN + threadCol];  // ONE load of B …
  for (uint resIdx = 0; resIdx < TM; ++resIdx)   // … reused 8 times
    threadResults[resIdx] +=
        As[(threadRow * TM + resIdx) * BK + dotIdx] * tmpB;
}

Read it with the miniature's numbers. Thread t owns column t of the tile. At dotIdx = d it loads Bs[d][t] once, into tmpB. Then for i from 0 to 7 it loads As[i][d] and adds As[i][d] × tmpB into accumulator i. Nine loads, eight multiply-adds, and the B value never touched memory again after the first load. The animation follows thread 5 through all eight values of d, with the line of the kernel being executed marked as it goes.

The count, per thread, per step of d: eight loads from As, one from Bs, nine in total, producing eight multiply-adds. That is 1.125 loads per FMA, down from 2.000. Put the other way, the instruction mix flips from two loads for every FFMA to nine loads for every eight FFMAs, so nearly half of what the scheduler issues is now arithmetic instead of a third. And there is a quieter gain riding along: the eight accumulators are independent of each other, so the scheduler can keep several multiply-adds in flight at once, which chapter 7 showed one accumulator could never do.

8.3From the miniature to the real block

If every thread now owns eight outputs, a block of the old 1,024 threads would cover 8,192 outputs, and the shared-memory tile that many outputs need would be awkward. Boehm's kernel 4 uses a 64 × 64 tile of C with BK = 8, and the numbers work out neatly: 4,096 outputs at eight per thread is 512 threads, the As chunk is 64 × 8 = 512 floats and the Bs chunk 8 × 64 = 512, so each thread copies exactly one element of each per chunk, coalesced, as in kernel 3. In the miniature the eight threads had to copy eight elements each; that is the only place the two differ.

Because the block tile grew from 32 × 32 to 64 × 64, the global-memory traffic improves as well, independently of everything above: reads per output fall from K/16 to K/32. A bigger tile means more reuse of each value fetched from DRAM, which is the same lever kernel 3 pulled. So kernel 4 changes two things at once, a taller thread tile that cuts the shared-memory traffic and a wider block tile that cuts the DRAM traffic, and it is worth keeping the two apart when reading the measurement.

8.4Predict, then measure

If shared-memory loads were the only thing that mattered, the ratio alone would predict a speedup of 2 ÷ 1.125 = 1.78×. Measured: 2,980 → 8,475 GFLOP/s, a 2.84× step. The rest comes from the two other changes: the halved DRAM traffic, and those eight independent accumulators giving the scheduler something to overlap.

What kernel 4 taught

Once a loaded number is in a register, reusing it costs nothing. The only question is how to arrange the work so that one thread holds several outputs that want the same number. Kernel 4 arranged it in one direction, along a column, and used the B sharing. It left the A sharing on the table: each A value is still loaded and used once.

Which makes the next move obvious. If stretching a thread's territory in one direction helped this much, what happens if we stretch it in two? That is kernel 5, and it is the chapter with the picture to keep.
