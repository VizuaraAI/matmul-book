Chapter 3 · Foundations

The machine a kernel sees: threads, warps, and three memories

The ten kernels are written in a vocabulary that assumes you already know what a warp is and which of three memories you meant. Here is that vocabulary, as mechanism rather than definitions.

Hardware · NVIDIA A6000, Ampere · 84 SMs · 10,752 lanes · three memories

So far everything has been arithmetic on paper. Chapter 1 counted the work, 137 GFLOP, and divided it by what the card can do to get a floor of 4.6 milliseconds. Chapter 2 put the memory clock next to the arithmetic clock and found that this multiply ought to be compute-bound with room to spare. Neither chapter needed to know anything about the chip beyond two numbers.

That ends here. From the next chapter on we're reading code that runs on a particular piece of silicon, and the code leans on a handful of hardware facts that it never states. I'd rather introduce those facts as mechanisms than as definitions, because the definitions are short and mostly useless on their own. Knowing that a warp is 32 threads tells you nothing. Watching what a warp does to a load instruction tells you why kernel 1 gets 1.3% of the machine and why kernel 2, which changes two lines, gets six times more — and those turn out to be the same fact seen twice.

There's no CUDA code in this chapter. Chapter 4 has the first kernel, nine lines of it, and everything below is something those nine lines quietly rely on.

3.1Threads, blocks, and the grid

When you launch a CUDA kernel you don't launch a thread. You launch a grid of blocks, and the hardware makes the threads. A block holds up to 1,024 of them. All 1,024 run on one streaming multiprocessor — one SM — and they share that SM's shared memory, which is the one place in this machine where threads can hand each other data cheaply.

Blocks, on the other hand, are strangers to each other. A block can't wait for another block, can't read another block's shared memory, and can't assume anything about when another block runs or whether it has run at all. The hardware hands blocks out to SMs as slots free up, in whatever order suits it, and when a block finishes, its slot takes the next one from the queue. That independence is why the same compiled kernel runs on a small GPU and a large one without anybody recompiling anything: with fewer SMs, the blocks simply queue for longer.

For our problem the shape works out like this. C is 4,092 × 4,092. Give each block a 32 × 32 tile of it — 1,024 threads, one per output element, which is the largest block the hardware allows. Then 4,092 ÷ 32 = 127.9, so we need 128 blocks across and 128 down. That's 16,384 blocks, and the last row and column of them hang over the edge of C, because 4,092 isn't a multiple of 32. One thread per element of C works out at about 16.7 million threads in all.

Eighty-four SMs and 16,384 blocks means each SM will work through roughly two hundred of them, one or a few at a time. Nothing in the kernel says which block goes where, and nothing may depend on it.

3.2The SM, and the warp as the unit of execution

An SM is the unit that actually runs anything, so let's open one up. Inside you'll find 128 FP32 lanes — the pieces that do the fused multiply-adds we counted in chapter 1 — a register file of 65,536 32-bit registers, up to 100 KB of shared memory with an L1 data cache sitting alongside it, and four warp schedulers.

The schedulers are the part to slow down on. Each one issues one instruction per clock, for one warp, to its own 32 lanes. Four schedulers, 32 lanes each, is where the 128 comes from. And notice what that arrangement rules out: the machine never issues an instruction for a thread. The smallest thing it can issue an instruction for is 32 threads at once.

Those 32 are a warp. A warp is 32 consecutive threads of a block — threads 0 to 31, then 32 to 63, and so on — so a block of 1,024 threads is exactly 32 warps. When a scheduler picks a warp and issues an FMA, all 32 lanes perform that FMA in the same cycle, each on its own registers, each producing its own result. NVIDIA's name for this is SIMT: single instruction, multiple threads.

Now apply that to a load, which is where this stops being trivia. A warp reaching A[x * K + k] does not issue one address. Thread 0 works out its address, thread 1 works out its own, all 32 do, and the 32 addresses go out together as a single request to the memory system. Whether that request is cheap or ruinous depends entirely on how those 32 addresses sit relative to one another, which is section 3.5 and most of chapters 4 and 5.

Which gives us the habit to build before any code: stop asking what a thread does, and start asking what its warp asks for. A thread's cost is an accounting fiction. The warp is what the hardware charges for.

Aside · what a stalled warp costs

An SM can hold at most 1,536 threads at once, which is 48 warps. Warps that are loaded onto it are called resident. When a resident warp stalls waiting for a load to come back, its scheduler doesn't wait with it — it switches to another resident warp that's ready, in the same cycle, at no cost. That's latency hiding, and it's the entire reason the number of resident warps is a thing anybody talks about. Chapter 10 makes a whole chapter of it, and shows that more resident warps is not automatically better.

3.3Three memories, three distances

A kernel can put a number in three places, and choosing between them is most of what the ten kernels are doing.

Registers are private to one thread. They're the fastest storage on the chip, and a value in a register is available in the same cycle the instruction uses it, so for our purposes a register read is free. You don't allocate them; the compiler does, out of the SM's 65,536 registers, and no thread may have more than 255. That register file is shared by every resident thread on the SM, which is why a kernel that wants a lot of registers per thread ends up with fewer threads resident. Chapter 9's kernel spends 64 registers per thread on accumulators alone and is faster for it.

Shared memory is a scratchpad on the SM, visible to every thread in the block and to nobody else. The program fills it explicitly — a kernel copies values there from global memory — and what it puts there stays until something overwrites it. A block may use 48 KB of the SM's 100 KB. Reading it takes roughly 20 to 30 cycles. That's the whole idea behind kernel 3: fetch a tile of A and B once into shared memory, then let all 1,024 threads read it from there instead of each going to DRAM for its own copy.

Global memory is the DRAM: 48 GB of GDDR6, 768 GB/s, visible to everything, and hundreds of cycles away. A, B and C live here, because nothing else is big enough. Every byte the kernel works on starts here and every byte of the answer ends here; the only question is how many times it makes the trip.

There are caches in between — 6 MB of L2 shared by all 84 SMs, and the L1 on each SM — and they hold whatever was recently touched. They help, sometimes a lot. But you can't tell them what to keep: shared memory is a cache you control, and L1 and L2 are caches that happen to you.

Put the latencies next to the arithmetic and the shape of the problem appears. One lane retires one FMA per clock. So four to six hundred cycles of waiting is four to six hundred multiply-adds that lane didn't do — and a kernel that goes to global memory for every operand of every FMA is idle almost all of the time, no matter how many warps you give it to switch between.

There are only two things to do about that: fetch fewer bytes, and fetch the bytes you do need into the near memories, where they can be read again for nothing. Kernel 2 does the first, by asking for its bytes in a better order. Kernel 3 does the second with shared memory, kernels 4 and 5 do it with registers, and kernel 10 adds a level in between.

3.4How a matrix sits in memory

One more piece before the sectors, and it's a dull one. Memory is one line of bytes. It has one dimension, and a matrix has two, so somebody has to decide how to flatten it.

C and CUDA use row-major order: all of row 0, then all of row 1, then row 2, laid out end to end. For a matrix with K columns, the element A[i][k] therefore lives at

base + (i * K + k) * 4        // 4 = sizeof(float)

bytes from the start. Which is why A[x * K + k] appeared in the kernel-1 code as a flat, one-dimensional index: that's what the hardware sees anyway, and CUDA doesn't pretend otherwise.

Two consequences fall out of that. Two neighbors in the same row are adjacent on the tape: 4 bytes apart. Two neighbors in the same column are a whole row apart: K × 4 bytes. For our matrices, with K = 4,092, that's 16,368 bytes between one element and the one directly below it.

Walking along a row and walking down a column look equally natural when you write the loop. They are not remotely the same thing to the memory system, and the next section says by how much.

3.5Sectors and lines

The memory system does not deliver floats. The smallest thing it will move is a 32-byte sector: eight consecutive floats, aligned. Ask for one of them and all eight come back, whether or not you wanted the other seven. Above the sector there's the cache line, 128 bytes, which is four sectors.

This isn't a quirk to be worked around. It's how DRAM and the caches are built — moving eight floats costs barely more than moving one, so the hardware always moves eight — and it turns a warp's 32 addresses into a bill.

Take a warp whose 32 threads want 32 consecutive floats. Those 128 bytes sit in four sectors, the memory system fetches four sectors, and every byte it moved gets used. Now take a warp whose 32 threads want one float from each of 32 different rows — the column walk from the last section, 16,368 bytes between neighbors. No two of those floats share a sector, so the memory system fetches 32 sectors: 1,024 bytes moved to deliver the 128 that were asked for. One byte in eight, or 12.5%.

Same 32 floats. Same instruction. Eight times the traffic, purely because of which 32 addresses went out together.

What to carry into chapter 4

Two remedies, one habit. The remedies: fetch less, and fetch into the near memories — registers and shared memory — where a value can be read again for nothing. The habit: think in warps, not threads. A single thread's loads have no cost you can reason about; a warp's 32 addresses do.

That's the machine. Grid, block, warp, lane; register, shared memory, global memory; row-major, sector, line. Nothing here is subtle, and none of it is specific to matrix multiplication — it's the same machine whatever you write for it.
