Chapter 5 · The memory-starved kernels

Kernel 2: memory coalescing

Two index lines change. The loop, the arithmetic and the thread count stay exactly as they were, and the kernel runs 6.4 times faster.

Kernel · sgemm_global_mem_coalesce · 1,986 GFLOP/s · 8.5% of cuBLAS · measured by Simon Boehm on an NVIDIA A6000

Chapter 4 ended with a diagnosis rather than a fix. Kernel 1 moved 1,056 bytes for every 64 FLOPs, and the reason had nothing to do with the arithmetic or the loop. It was that the 32 threads of a warp asked for 32 floats sitting in 32 different rows of A, and memory serves whole 32-byte sectors whether you wanted them or not. Thirty-two addresses, thirty-two sectors.

This chapter changes the addresses and nothing else.

5.1Two lines change

Here is kernel 2. Two lines differ from kernel 1 — the highlighted ones — and everything below them is untouched.

// one 1-D block of BLOCKSIZE * BLOCKSIZE = 1,024 threads, BLOCKSIZE = 32
const int cRow = blockIdx.x * BLOCKSIZE + (threadIdx.x / BLOCKSIZE);   // row
const int cCol = blockIdx.y * BLOCKSIZE + (threadIdx.x % BLOCKSIZE);   // column

if (cRow < M && cCol < N) {
    float tmp = 0.0;
    for (int i = 0; i < K; ++i)
        tmp += A[cRow * K + i] * B[i * N + cCol];   // 2 loads, 2 FLOPs
    C[cRow * N + cCol] = alpha * tmp + beta * C[cRow * N + cCol];
}

The block is one-dimensional now: 1,024 threads numbered 0 to 1,023. The kernel takes that single number and splits it in two. Divide by 32 and you get a row inside the 32 × 32 tile; take the remainder and you get a column. Threads 0 to 31 — which is warp 0 — all divide to 0 and leave remainders 0 through 31, so warp 0 owns row 0 of the tile, columns 0 to 31.

Why threadIdx.x specifically? Because that's the index the hardware uses to build warps. Threads inside a block are numbered with threadIdx.x running fastest, and consecutive thread numbers are packed 32 at a time: threads 0 to 31 are warp 0, 32 to 63 are warp 1, and so on. Whatever threadIdx.x feeds becomes the thing that varies across a warp, and therefore the thing that decides what the warp's 32 addresses look like. In kernel 1 it fed the row of C, so the addresses walked down a column of A. Here it feeds the column, so they walk along a row of B.

Kernel 1 gave warp 0 thirty-two outputs too. It just stacked them vertically. Read as a rewrite this looks like nothing at all, and the difference only appears when you ask where the warp's 32 addresses land at the instant the load is issued — which is the only thing memory ever sees.

5.2The new request at k = 0

Take the first pass of the loop, i = 0, the same moment we watched in chapter 4.

The load from A is A[cRow * K + i], and every thread in warp 0 has cRow = 0 and i = 0. All 32 addresses are the same address. The memory system fetches the sector holding A[0][0] once and broadcasts the value to all 32 threads: one sector, 32 bytes. It's the free case that B enjoyed in kernel 1, and now A gets it instead.

The load from B is B[i * N + cCol], and cCol runs 0, 1, 2, … 31 across the warp. Those are 32 consecutive floats of row 0 of B. Row-major storage puts consecutive elements of a row next to each other, so the request is one unbroken run of 128 bytes. A sector is 32 bytes and 128 divides by 32 exactly, so the run is precisely four sectors and every byte in all four is wanted by somebody. The four sectors divide the warp neatly: sector 0 holds B[0][0] through B[0][7], so it serves threads 0 to 7 and nobody else. Eight threads per sector, four sectors, thirty-two threads. Nothing travels for nothing.

The bytes the warp actually wants haven't changed. There are still 132 of them, because the warp is still doing the same 64 FLOPs on the same data. What changed is what the memory system had to move in order to deliver them: 1,056 bytes before, 160 now.

5.3Predict, then measure

1,056 ÷ 160 = 6.6.

That number is a prediction, and I'd rather state it before looking at the answer. Chapter 4's claim was that kernel 1 is limited by memory and by nothing else — that the arithmetic units spend essentially all of their time waiting for bytes. If that's true, and if kernel 2 needs 6.6 times fewer bytes to do identical work, then kernel 2 should be about 6.6 times faster. Kernel 1 ran at 309 GFLOP/s, so we should see roughly 309 × 6.6 = 2,039.4.

Boehm measures 1,986.5 GFLOP/s. That is a 6.4× speedup, and it sits within 3% of a number we got by counting sectors on paper.

This is the part of the worklog I'd point at first if someone asked why any of this is worth learning. Nothing was tuned here. No parameter was swept. A model said the kernel was starving for bytes in a particular shape, the shape got fixed, and the machine moved by almost exactly the factor the model predicted. Boehm's profiler confirms it from the other side too: useful memory throughput rises from about 15 GB/s to about 110 GB/s.

Kernel 2 is 8.5% of cuBLAS. The naive kernel was 1.3%. That is what two index lines bought.

5.4What coalescing means

The name for what just happened is memory coalescing, and the name misleads a little. It sounds like something the hardware does for you, as though the GPU inspects your 32 addresses, notices they're neighbors, and cleverly merges them into a single request. It doesn't. The memory system does the same thing on every load it has ever served: it fetches whole 32-byte sectors, as many as it takes to cover the addresses it was handed. The only variable is how many that is, and that is decided entirely by your indexing.

Key

Coalescing isn't an optimization the GPU performs. It's a property the 32 addresses of a warp either have or lack. Same hardware, same rule, different addresses, 6.4×.

Here is the same warp — 32 threads, one float each, 128 bytes wanted every time — at four different strides.

Two things in that table are the ones to keep. The first is that the bytes the warp wants never change; only the bytes that move do. The second is that the damage tops out. At stride 1 the request is four sectors. At stride 2, eight. By stride 8 — that's 32 bytes, exactly one sector — each wanted float has a sector to itself, and you're at 32 sectors and 12.5% useful. Increasing the stride past that changes nothing at all: a column of A, whose neighbors are 16,368 bytes apart, costs the same 32 sectors as a stride of 8. Kernel 1's pattern wasn't bad because its stride was enormous. It was bad because its stride was one sector or more, which is all it takes to hit the floor.

The practical version of this is short. Whatever a warp loads, look at what varies across its 32 threads, and check that the variation lands on consecutive addresses. An array indexed by threadIdx.x at unit stride is coalesced. The same array indexed by threadIdx.x * 32 is not, and it will cost eight times the traffic no matter how carefully the rest of the kernel is written.

5.5Why not 768 GB/s yet

110 GB/s of useful throughput, on a part that can move 768. If every request is now the right shape, why isn't the kernel saturating the bus?

Because the requests are the right shape and there are still far too many of them.

Count what one block reads. A block computes a 32 × 32 tile of C, so between them its threads need 32 whole rows of A — a strip of 32 × 4,092 floats — and 32 whole columns of B. Now count the blocks. 4,092 ÷ 32 is 127.9, so there are 128 tiles along each edge of C and 16,384 blocks in all. Every one of the 128 blocks in the first row of tiles reads that same row strip of A. Each strip is fetched 128 times over, and every column strip of B gets the same treatment.

That is only the redundancy between blocks. Inside a block it's worse: the thread that owns C[0][0] and the thread that owns C[0][1] both walk the whole of row 0 of A, so within one tile every value of A is read 32 times. That one is chapter 6's subject.

Add it up and kernel 2 issues exactly the loads kernel 1 issued: 137 billion of them, 548 GB requested. Not a single load was removed. What changed is that the bytes now arrive in useful shapes, so far less pointless traffic is generated per load.

Aside · what the L2 cache was hiding

If kernel 1 really pulled all 548 GB out of the memory chips at 768 GB/s, it would take 0.71 seconds, and 137 GFLOP in 0.71 seconds is 192 GFLOP/s. Kernel 1 measured 309, comfortably above that floor, which means a good share of those 137 billion loads never reached DRAM at all. The L2 cache served them, because 128 blocks were asking for the same strip. Caches soften a bad access pattern; they don't repair it. That is why kernel 1 still only got 1.3% of the machine, and why fixing the pattern was worth another 6.4× on top of everything the cache was already doing.

So the shape of each request is fixed and the number of requests is untouched. Kernel 3 goes after the number. It loads one tile of A and one tile of B into shared memory — the fast scratchpad on the SM that a whole block can read — and lets all 1,024 threads work out of that instead of going back to global memory 32 times each. That's the next chapter.
