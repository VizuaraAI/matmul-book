Chapter 7 · The memory-starved kernels

Why kernel 3 disappointed: the bottleneck moved

A 32× cut in memory traffic bought 1.5× in speed. That gap is not something to shrug at. It is the most useful measurement in the book, because it says exactly where the time went instead.

Hinge · kernel 3 at 2,980 GFLOP/s · 9.9% of the 30 TFLOP/s peak · the resource that ran out next

Kernel 3 cut its global-memory traffic by a factor of 32 and got 1.5× for it: 1,986 to 2,980 GFLOP/s. If global memory had still been the limit, a 32× cut would have produced something close to a 32× speedup. It didn't, so global memory was no longer what the kernel was waiting on. Something else became the limit while we were busy fixing DRAM, and this chapter finds it. Everything from kernel 4 onward is an attack on what we find here.

The tool is the only rule that ever matters in this business: a kernel's running time is set by whichever resource runs out first. So take the resources one at a time and ask, for each of them, how much of it a single multiply-add costs. Three candidates are left now that DRAM is out of the picture: the instruction issue slots, the shared-memory pipeline, and the arithmetic units themselves.

7.1Count the instructions

Here is kernel 3's inner loop again, and underneath it, roughly what the compiler turns it into. One line of C++ becomes three machine instructions: two loads from shared memory and one fused multiply-add. (The real machine code also carries address arithmetic and loop control; the compiler unrolls the loop to amortize those. The three instructions below are the part that scales with the work.)

tmp += As[threadRow * 32 + d] * Bs[d * 32 + threadCol];

LDS   R2, [As + threadRow*128 + d*4]     // load one word from shared memory
LDS   R3, [Bs + d*128 + threadCol*4]     // load one word from shared memory
FFMA  R1, R2, R3, R1                     // R1 = R2 × R3 + R1   (tmp, in a register)

Now the hardware side, from chapter 3. An SM has four warp schedulers, and each can issue one instruction per clock. That is the entire budget: four instructions per cycle, for everything the SM does. Each scheduler drives 32 FP32 lanes, and those lanes can accept a new multiply-add every cycle. If two out of every three instructions a warp issues are loads, then at most one cycle in three carries an FFMA, and the lanes can never be more than a third busy, before anyone has waited for anything.

7.2Count the words shared memory can serve

The second limit points the same way. Shared memory is built from 32 banks, and each bank can hand out one 4-byte word per cycle. Consecutive words live in consecutive banks, so a warp that reads 32 consecutive words touches all 32 banks once and is served in a single cycle. That is the best case, and kernel 3's read of Bs is exactly it: thread t reads Bs[d][t]. Its read of As is the other happy case: all 32 threads of the warp want the same word (they share a threadRow), so one bank answers and the value is broadcast.

Add it up for the whole SM. Shared memory can supply 32 words per cycle, at most. The 128 lanes, if they were all doing multiply-adds every cycle, would want two words each: 256 words per cycle. Supply is an eighth of demand. So even ignoring instruction issue entirely, operand supply alone caps this loop near 16 multiply-adds per cycle, an eighth of the machine's arithmetic peak. Counting the broadcast on As, which costs one bank instead of 32, the cap is nearer a quarter. Kernel 3 measures 2,980 GFLOP/s against a 30,000 peak: 9.9%. It is pressed right up against that wall.1

1This is deliberately the simplest model: it ignores bank conflicts and latency hiding, and it treats every cycle as available. It is not meant to predict the number, only to show which resource the kernel is leaning on.

7.3Where kernel 3 actually spends its time

Boehm's profiler confirms the diagnosis directly. The dominant reason its warps are stalled is what NVIDIA calls MIO throttle: warps queueing for the memory-input/output pipeline, which is the path shared-memory instructions take. Not waiting on DRAM, and not waiting on busy arithmetic units. The data is close by now. What costs is that reaching for it burns an instruction slot and a bank access every single time.

It is tempting to blame occupancy instead. Kernel 3 runs one block of 1,024 threads per SM, which is 32 of the 48 warp slots: 66%. That sounds like the sort of number that explains a slow kernel. It isn't, and the cleanest evidence comes two chapters from now: kernel 5 will have lower occupancy than kernel 3 and run five times faster. Chapter 10 does the occupancy arithmetic properly. For now, the honest reading of the profiler is that the warps that are resident are stuck in a queue for shared memory, and adding more warps to the queue would not shorten it.

7.4The other thing wrong with the loop

Look at the loop one more time. Every iteration reads tmp, adds to it, and writes it back. The next iteration cannot start its addition until the previous one has produced its result, because they use the same register. That is a dependency chain, 32 links long per chunk, and a fused multiply-add takes about four cycles to deliver its answer. With one accumulator, a thread can never have more than one multiply-add in flight.

Kernel 4 will hand each thread eight independent accumulators, which the scheduler can keep in flight together. That is a second, quieter reason it goes faster than its load count alone predicts, and it is worth noticing now so the next chapter's measurement doesn't look like magic.

7.5The number to watch

All three findings point at the same ratio: how many shared-memory loads the kernel spends for each multiply-add. Kernel 3 spends two. The supply side says what the ratio would have to be for the lanes to stay busy: 32 words per cycle divided by 128 multiply-adds per cycle is 0.25 loads per FMA. That is the target, and it is eight times below where we are.

The hinge of the book

Kernels 4 and 5 are one question asked twice: when can a single load serve more than one multiply-add? The answer is in the definition of C, where the same operand shows up in many outputs. Give one thread several outputs that share an operand, and one load feeds all of them. Kernel 4 does this in one direction and reaches 1.125 loads per FMA. Kernel 5 does it in both and reaches 0.25.

So the disappointment was worth having. It told us the memory system had stopped being the problem, which is what every chapter before this one was working toward, and it handed us the next problem with a number attached. The next chapter takes that number from 2 to 1.125, and the kernel from 12.8% to 36.5%.
