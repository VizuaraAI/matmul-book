Chapter 6 · The memory-starved kernels

Kernel 3: caching a tile in shared memory

Inside one block, every number is fetched thirty-two times. This kernel fetches it once, into a scratchpad the whole block can read — and gets a lot less for it than the arithmetic suggests.

Kernel · sgemm_shared_mem_block · 2,980 GFLOP/s · 12.8% of cuBLAS · measured by Simon Boehm on an NVIDIA A6000

Kernel 2 fixed the shape of every request and left the number of requests exactly where kernel 1 had it: 137 billion loads, 548 GB asked for. Chapter 5 ended by naming the two kinds of redundancy hiding behind that number. Between blocks, all 128 blocks along a row of tiles read the same row strip of A. Inside a block, the thread that owns C[0][0] and the thread that owns C[0][1] both walk the whole of row 0 of A, and each of them fetches it separately.

This chapter is about the second one. It has a number attached, and the number is 32.

6.1What one block needs

Follow one block — say the one computing the 32 × 32 tile in the top-left corner of C. Its 32 rows of output depend on rows 0 through 31 of A, every one of their 4,092 columns. Its 32 columns of output depend on columns 0 through 31 of B, all 4,092 rows. Nothing else in either matrix can change this block's answers. Count them: 2 × 32 × 4,092 = 261,888 distinct numbers, and that is everything the block will ever need.

Now count what kernel 2's block actually pulls in. There are 1,024 threads, each runs the k-loop 4,092 times, and each pass issues two loads. That is 1,024 × 4,092 × 2 = 8,380,416 loads.

8,380,416 ÷ 261,888 = 32.

Every number the block needs, it drags across the bus 32 times. Not a value here and there — all 261,888 of them, exactly 32 times each, and the 32 isn't an accident of the numbers.

This is a different count from chapter 5's. There the waste was between blocks: 128 blocks along a row of tiles, each pulling in the same strip of A. Here we are inside a single block, counting only what that one block does on its own, and the two redundancies stack. Kernel 3 goes after this one and leaves the other alone — the between-block re-reads are the ones the L2 cache has been quietly absorbing, as chapter 5's aside worked out.

6.2Where the 32 comes from

Take one number: A[0][7]. Which threads want it?

Every thread whose output sits in row 0 of the tile. A thread computing C[0][j] walks the whole of row 0 of A whatever j is, so on the eighth pass of its loop it asks for A[0][7]. There are 32 such threads, one per column of the tile, and each of them issues its own load. Thirty-two round trips to global memory for a number that hasn't changed since the kernel launched.

B is the same picture with the axes swapped. B[3][9] is wanted by every thread whose output is in column 9 of the tile: 32 threads, one per row, each fetching it separately.

So the 32 is the tile's edge length, seen from two directions. And the fix writes itself: fetch each value once, and put it somewhere all 32 threads can reach.

A register won't do. A register belongs to one thread and no other thread can see it, which is the same property that made it free to read. Shared memory is the other thing on the SM: a scratchpad of up to 48 KB per block, sitting physically on the chip beside the arithmetic units, visible to every thread of that block. Nothing arrives there by accident — you write the copy yourself, as an ordinary assignment — and once a value is in it, reading it costs on the order of 20 to 30 cycles instead of the several hundred a trip to DRAM costs.

The contrast with a cache is the part to keep. A cache decides for you. It holds what you touched recently, by a policy you don't control, and it may or may not still have your value by the time you come back for it — which is exactly why chapter 5 could say the L2 softens a bad access pattern without repairing it. Shared memory decides nothing. It holds what you put there, for as long as you leave it there, and if you want a value in it you have to write the line that copies it. That is more work, and the extra work is the whole reason it can be counted on.

6.3Why we can't preload everything

The obvious move is to copy all 261,888 numbers into shared memory once at the start and never touch global memory again. It doesn't fit, and it isn't close.

A's strip is 32 × 4,092 floats, which is 523,776 bytes, about 512 KB. B's strip is another 512 KB. The budget is 48 KB. We are over by a factor of about 21.

But the loop is an accumulation, and an accumulation doesn't need all of its terms at once. tmp += A[…] * B[…] can eat the k dimension in pieces, as long as the pieces cover it in the end. So chop k into chunks of 32.

One chunk of A is then a 32 × 32 square: 1,024 floats, 4 KB. One chunk of B is another 4 KB. Eight kilobytes for a pair, comfortably inside the 48. And 4,092 ÷ 32 = 127.9, so the k dimension breaks into 128 chunks, the last of them partial.

Hold one pair, add its 32 products into the running total, throw it away, load the next pair. The register holding the total is never reset, so after 128 rounds it holds the full 4,092-term dot product — the same number kernel 2 computed, out of a thirty-second of the traffic.

6.4The cooperative load, and one chunk step by step

Here is the kernel. It is still one thread per output element, and the inner arithmetic is still one multiply-add per k step; what's new is the copy at the top of the loop and the two barriers around it.

// BLOCKSIZE = 32; one 1-D block of 1,024 threads computes the tile at (cRow, cCol)
const uint threadRow = threadIdx.x / BLOCKSIZE;   // 0 … 31
const uint threadCol = threadIdx.x % BLOCKSIZE;   // 0 … 31, consecutive across a warp

__shared__ float As[BLOCKSIZE * BLOCKSIZE];      // 4 KB, lives on the SM
__shared__ float Bs[BLOCKSIZE * BLOCKSIZE];      // 4 KB

A += cRow * BLOCKSIZE * K;                        // this block's row strip of A
B += cCol * BLOCKSIZE;                            // this block's column strip of B
C += cRow * BLOCKSIZE * N + cCol * BLOCKSIZE;

float tmp = 0.0;                                // the running total, in a register
for (int bkIdx = 0; bkIdx < K; bkIdx += BLOCKSIZE) {
    As[threadRow * BLOCKSIZE + threadCol] = A[threadRow * K + threadCol];
    Bs[threadRow * BLOCKSIZE + threadCol] = B[threadRow * N + threadCol];
    __syncthreads();                              // nobody reads until everybody has written

    A += BLOCKSIZE;                               // slide the window along k
    B += BLOCKSIZE * N;

    for (int dotIdx = 0; dotIdx < BLOCKSIZE; ++dotIdx)
        tmp += As[threadRow * BLOCKSIZE + dotIdx] * Bs[dotIdx * BLOCKSIZE + threadCol];

    __syncthreads();                              // nobody overwrites until everybody has read
}
C[threadRow * N + threadCol] = alpha * tmp + beta * C[threadRow * N + threadCol];

The three lines above the loop are bookkeeping: they move each pointer to where this block's work begins, A to the top of its 32-row strip, B to the left edge of its 32-column strip, C to the corner of its tile. Everything after that is written as though the block were the whole problem — threadRow and threadCol run 0 to 31 and mean "inside this tile" — which is why the two copies look like they are reading the top-left corner of A and B when they are usually reading somewhere in the middle of a 4,092 × 4,092 matrix. The two bumps inside the loop, A += BLOCKSIZE and B += BLOCKSIZE * N, slide that window along k: 32 columns to the right in A, 32 rows down in B.

Now look at the copy. A chunk holds 32 × 32 = 1,024 elements and the block has 1,024 threads, so each thread copies exactly one element of A and one of B. No loop, no leftover, no thread sitting idle. And the indexing is the one chapter 5 arrived at: threadCol is threadIdx.x % 32, so it runs 0 to 31 across a warp while threadRow stays fixed, which makes the warp's 32 addresses for A[threadRow * K + threadCol] consecutive. The copy is coalesced. Two thousand and forty-eight global loads for the whole block, and that is the entire business this chunk has with global memory.

Now follow thread (5, 9) — the one that owns C[5][9] of the tile — through a single chunk.

It starts by copying its one element of A into As[5][9] and its one element of B into Bs[5][9]. Two loads from global memory, and they are the slow kind, hundreds of cycles each. Then it reaches the first __syncthreads() and stops. When it is let through, it runs the inner loop 32 times: tmp += As[5][d] * Bs[d][9] for d from 0 to 31. That is 32 reads along row 5 of As, 32 reads down column 9 of Bs, and 32 multiply-adds — and every one of those 64 reads comes out of shared memory, with global memory untouched. Then the second __syncthreads(), and then the window over row 5 of A slides 32 columns to the right and the whole thing happens again, into the same register, which nobody reset.

The sharing never went away. Row 5 of As is still read by all 32 threads that own row 5 of the tile, and column 9 of Bs is still read by the 32 threads in column 9. What changed is where they read it from: one slow trip to global memory and then 32 fast reads out of the scratchpad, instead of 32 slow trips.

And tmp is exactly where kernel 2 left it — a register, private to the thread, not written to memory until the last line of the kernel. Nothing about the tiling touches it. What the kernel has now is all three levels of the hierarchy in play at once: a register for the running total, shared memory for the operands of the chunk in front of it, global memory for everything it hasn't reached yet. Every kernel from here on keeps that shape; what changes is how much of the work each level is asked to carry.

6.5What a barrier is

Two lines in that loop do no arithmetic at all, and the kernel is wrong without either of them.

__syncthreads() makes every thread of the block stop at that line until all 1,024 of them have reached it. A meeting point, nothing more.

You need it because threads don't run in lockstep. A block's 32 warps are handed to the SM's four schedulers, and a scheduler runs whichever of its warps is ready — a warp waiting on a load steps aside and another one runs in its place. Some warps get a long way ahead. Without the first barrier, a thread that has finished its own copy can walk straight into the inner loop and read As[5][17] before the thread responsible for As[5][17] has written it. What it gets is whatever was sitting in that slot: the previous chunk's value, or uninitialized memory on the first chunk. The answer comes out wrong, sometimes, depending on how the warps happened to be scheduled, which is about the worst kind of wrong there is.

The second barrier prevents the mirror image. Once a fast thread finishes its 32 multiply-adds it wants to start the next chunk's copy, and that copy overwrites As and Bs. If a slow thread is still on d = 20 of its inner loop, the values under it change while it is reading them.

There is no cheaper version of this. You can't replace either barrier with an argument about which warp gets there first, because there is no such argument available: the schedulers run whichever warp is ready, and which one that is depends on what all the others happened to be waiting for. The barrier is the only thing in the kernel that makes any statement about order.

Aside · two bugs, one loop apart

Both failures are read-write races on shared memory and they are symmetric: the first barrier stops a read from overtaking a write, the second stops a write from overtaking a read. Both are timing-dependent, so a kernel missing one of them can pass a test and fail in production, or pass on one GPU and fail on the next. The fast threads do pay for the barriers — they stand at the line doing nothing until the last warp turns up — and that waiting is real, measurable time. It buys an answer that is the same every run.

6.6How that turns into FLOPs

Per chunk, per block: 2,048 global loads, 65,536 shared-memory reads, 32,768 multiply-adds. Over 128 chunks the block issues 262,144 global loads, against kernel 2's 8,380,416. That is the factor of 32 we set out to get, and it lands almost exactly on the 261,888 distinct values the block needs. Each number is fetched once.

Per element of C the same thing reads: kernel 2 spent 2K = 8,184 global loads on every output; kernel 3 spends K/16 = 256. That second number comes straight out of the loop — each thread does two global loads per chunk, one element of A and one of B, and there are 128 chunks.

Key

Shared memory didn't remove the sharing. It moved it: one slow trip to global memory, then 32 fast reads of the scratchpad, in place of 32 slow trips.

Boehm measures 2,980.3 GFLOP/s, up from 1,986.5. That is 1.5×, and it takes the kernel from 8.5% of cuBLAS to 12.8%.

A 32× cut in global traffic buying 1.5× in speed is a large miss, not a small one. If global memory had still been the thing this kernel waited on, cutting its traffic by 32 would have shown up as something close to 32×. Chapter 5 made a prediction of exactly that shape, out of nothing but a sector count, and it landed within 3%. Run the same reasoning here and it is off by a factor of twenty.

The reasoning isn't what broke; the premise underneath it is. Global memory stopped being the limit somewhere between kernel 2 and this one, and the kernel is now waiting on something else. Naming that something is the next chapter's job, and it is the hinge of the book: every kernel from 4 onward is an attack on what chapter 7 finds.
