Chapter 11 · The last mile

Kernel 6: vectorized memory access

Four 32-bit loads become one 128-bit load, and a transposed shared-memory tile makes that legal for A as well as B. The bytes don't change; the instruction count does.

Kernel · sgemmVectorize · 18,237 GFLOP/s · 78.4% of cuBLAS · measured by Simon Boehm on an NVIDIA A6000

From here the remaining gains are smaller and more specialist. Kernel 5 got us to 68.7% of cuBLAS, and chapter 7's diagnosis has largely been answered: the shared-memory traffic per multiply-add is at the supply line, DRAM stopped being the limit three kernels ago. What is left to trim is instructions. We are close enough to the arithmetic limit that every load instruction the scheduler issues is a slot it didn't spend on an FFMA, and this chapter is about issuing fewer of them for the same bytes.

11.1Four loads or one

A thread that needs four consecutive floats can get them with four 32-bit load instructions, or with one 128-bit load instruction. The bytes that move are identical, sixteen either way. The instruction count is four times lower, and instruction issue is now part of what limits us. CUDA exposes the wide load through the float4 type: a struct of four floats that the hardware moves as a unit.

There is a catch, and it is why the change needs an explicit cast in the source rather than a compiler flag. The compiler cannot know that a pointer someone hands it is 16-byte aligned, and a 128-bit load from an unaligned address is illegal. So Boehm's kernel 6 tells it, with reinterpret_cast<float4*>: a promise that this address is a multiple of sixteen, which the tile layout guarantees. With that promise the compiler emits LDG.E.128 for global loads and LDS.128 for shared-memory loads instead of four LDG.E or four LDS.

// global → shared, four floats of A at a time (transposed on the way in)
float4 tmp = reinterpret_cast<float4 *>(&A[innerRowA * K + innerColA * 4])[0];
As[(innerColA * 4 + 0) * BM + innerRowA] = tmp.x;
As[(innerColA * 4 + 1) * BM + innerRowA] = tmp.y;
As[(innerColA * 4 + 2) * BM + innerRowA] = tmp.z;
As[(innerColA * 4 + 3) * BM + innerRowA] = tmp.w;

// global → shared, four floats of B at a time, no transpose needed
reinterpret_cast<float4 *>(&Bs[innerRowB * BN + innerColB * 4])[0] =
    reinterpret_cast<float4 *>(&B[innerRowB * N + innerColB * 4])[0];

11.2Why As has to be stored transposed

Look at the four lines that store tmp. They don't write the four floats next to each other; they scatter them into four different rows of As, one per value of k. That is the subtlety of this kernel, and the reason is in kernel 5's inner loop. Each step of k, the thread copies its eight A operands into registers by walking down a column of As: regM[i] = As[(threadRow × 8 + i) × BK + dotIdx]. In kernel 5's layout, rows of As are 8 floats long, so those eight values are 32 bytes apart from each other. Not contiguous, so not a vector load. Eight separate LDS instructions, every step.

Store As transposed, k-major instead of m-major, and the column walk becomes a row walk: the eight values a thread wants for a given k are now eight neighbors, which is exactly two LDS.128. Bs never had the problem, because regN reads along a row of Bs to begin with. The animation shows both layouts as the one-dimensional memory they really are.

The price of the transpose is paid on the way in. Each thread loads four consecutive floats of A from global memory with one wide load, but then has to write them to four different rows of As with four scalar stores, because the four values it fetched belong to four different k. B pays nothing: four floats in, one wide store out. It is a good trade, because the global-to-shared copy happens once per chunk while the shared-to-register copy happens eight times per chunk, once per k.

11.3What it bought

Count the instructions in one step of k, per thread. Kernel 5 issues eight loads for regM, eight for regN, and sixty-four FFMAs: eighty instructions, of which 80% are arithmetic. Kernel 6 issues two wide loads for regM, two for regN, and the same sixty-four FFMAs: sixty-eight instructions, 94% arithmetic. The bytes read from shared memory are unchanged. Only the number of times the scheduler has to say "load" went down.

Boehm measured the two halves of the change separately. Transposing As so that its loads vectorize was worth about 500 GFLOP/s on its own, around 3%; the wide global loads and stores account for the rest of the 14%. Here is what the change looks like at the machine-code level, in his listing: the shared-memory reads that used to be single-word loads become pairs of 128-bit ones.

// before (PTX): one word at a time
ld.shared.f32   %f91, [%r8+3456];

// after (SASS): sixteen bytes at a time
LDS.128 R8,  [R2]
LDS.128 R12, [R2+0x20]

That is the end of the changes that come from reasoning about the memory system directly. The kernel now moves close to the minimum bytes, at close to the minimum instruction count, in the layout the hardware wants. What remains is that it has five free parameters, and nobody knows which combination of them is best for this particular chip. The next chapter stops reasoning and starts measuring.
