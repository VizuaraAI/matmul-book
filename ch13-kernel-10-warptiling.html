Chapter 13 · The last mile

Kernel 10: warptiling

Block tile, warp tile, thread tile. The warp was always the unit that runs; kernel 10 makes it a unit of the tiling too, and the last ten percent follows.

Kernel · sgemmWarptiling · 21,779 GFLOP/s · 93.7% of cuBLAS · measured by Simon Boehm on an NVIDIA A6000

Until now the tiling has had two levels. The block tile maps to an SM: a block owns a 128 × 128 patch of C and stages chunks of A and B for it in shared memory. The thread tile maps to a thread's registers: each thread owns an 8 × 8 patch of the block's and accumulates it there. But chapter 3 established that the hardware has a third level in between. The warp, the group of 32 threads that a single scheduler issues instructions for, is the real unit of execution, and nothing in kernels 3 to 9 acknowledges it. Which thread sits in which warp is an accident of numbering.

Kernel 10 makes the warp an explicit level of the hierarchy. Each warp owns a fixed patch of the block's tile, and each thread's outputs are laid out so that the 32 threads of a warp, taken together, touch a compact, predictable region of shared memory at every step. The arithmetic is unchanged. What changes is who computes what, and therefore which values sit next to which in shared memory and in the register file.

13.1Three levels, all visible at once

Here are Boehm's settings for the A6000. The block tile is still 128 × 128 with a chunk width of 16. The block has 128 threads, which is four warps, and each warp owns a 64 × 64 warp tile, so the four warps sit in a 2 × 2 arrangement over the block tile. Inside a warp tile, the layout has one more wrinkle. The warp tile is split into four subtiles of 64 × 16, side by side, and each thread owns an 8 × 4 patch in every subtile. So a thread's 128 outputs are four separate 8 × 4 patches, sixteen columns apart.

13.2One step of k, for one warp

The inner loop is kernel 5's outer product, one level up. For each step of k a thread stages its A operands, eight of them (its eight rows), and its B operands, sixteen of them (four columns in each of the four subtiles), and then does 8 × 16 = 128 multiply-adds from registers. Twenty-four loads for a hundred and twenty-eight FMAs: 0.1875 loads per multiply-add, down from 0.25. Each staged A value is used sixteen times now instead of eight, and each B value eight times as before.

for (uint dotIdx = 0; dotIdx < BK; ++dotIdx) {
  // stage this thread's 8 A operands: its 8 rows of the warp's 64, at column dotIdx of the transposed As
  for (uint i = 0; i < TM; ++i)
    regM[i] = As[dotIdx * BM + warpRow * WM + threadRowInWarp * TM + i];
  // stage its 16 B operands: 4 columns in each of the 4 subtiles
  for (uint sub = 0; sub < WNITER; ++sub)
    for (uint i = 0; i < TN; ++i)
      regN[sub * TN + i] = Bs[dotIdx * BN + warpCol * WN + sub * WSUBN + threadColInWarp * TN + i];
  // 8 × 16 = 128 multiply-adds, no memory touched
  for (uint sub = 0; sub < WNITER; ++sub)
    for (uint m = 0; m < TM; ++m)
      for (uint n = 0; n < TN; ++n)
        threadResults[m * (WNITER * TN) + sub * TN + n] += regM[m] * regN[sub * TN + n];
}

Now look at the same step from the warp's point of view, which is the point of the kernel. The 32 threads of a warp are arranged 8 × 4 inside a subtile: eight thread-rows of four. The four threads in a thread-row want the same eight A values, so those loads are broadcasts, and the eight thread-rows between them want the warp's 64 consecutive floats of the transposed As: one contiguous 256-byte run. On the B side, for each subtile the four thread-columns want four adjacent groups of four floats: one contiguous 64-byte run, wanted by eight threads each. So at every step, the whole warp's shared-memory appetite is a handful of short contiguous runs, and the banks serve them without collisions.

13.3Why relabelling who computes what buys ten percent

Nothing about the arithmetic changed, so the gain has to come from the supply side, and it comes from three places, all of them consequences of the warp being the real unit of execution. The first is the ratio above: 0.1875 loads per FMA, a quarter fewer shared-memory instructions than kernel 9 for the same arithmetic. The second is that each warp's reads are compact and predictable, so its 32 lanes hit the banks in clean runs instead of colliding, which is the thing kernels 7 and 8 tried to buy with padding and index tricks, delivered here by layout alone. The third is that each warp's work is independent of the other three warps', so the four schedulers on the SM each have a warp with a long, conflict-free run of instructions to issue.

The price is the one chapter 10 would predict. A thread now holds 128 accumulators plus 24 operands, so it needs at least 152 registers, and the block has only 128 threads to spread the cooperative load over. Both are fine here because the kernel is now so far into the instruction-bound regime that instruction-level parallelism is doing the latency hiding, and 128 independent multiply-adds per step is a great deal of it.

13.4The last mile, in one view

Stepping back over the four kernels since the outer product: kernel 6 shaved load instructions with 128-bit loads and a transposed tile; kernel 9 found a wider chunk by search; kernel 10 aligned the tiling with the warp. Each is worth a few percent, and together they take 68.7% to 93.7%. None of them changed a byte of the traffic budget that the first five kernels fought over. That is what "the last mile" means here: the supply chain is solved, and what remains is fitting the instruction stream to the machine.
