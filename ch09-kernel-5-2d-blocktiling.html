Kernel 5: 2D blocktiling and the outer product

Give one thread an 8 × 8 patch of C, and sixteen numbers in registers turn into sixty-four multiply-adds. This is the picture to keep if you keep only one from the book, and we watch the kernel produce it, load by load.

Kernel · sgemm2DBlocktiling · 15,972 GFLOP/s · 68.7% of cuBLAS · measured by Simon Boehm on an NVIDIA A6000

Chapter 8 found two kinds of sharing in the definition of C. Outputs stacked in a column share their B operand; outputs side by side in a row share their A operand. Kernel 4 used the first and ignored the second. Its thread owns a tall thin strip, eight outputs in one column, so it gets to reuse each B value eight times and gets nothing at all on A. That is exactly why it still pays eight separate A loads for its eight multiply-adds, and why its ratio stopped at 1.125 loads per FMA.

The fix is to make the thread's territory square. Give it an 8 × 8 patch of C and both sharings come into play at once. This chapter is that one change, watched closely, because the arithmetic it produces has a name and a shape worth knowing on sight.

9.1The sharing kernel 4 ignored

The 8 × 8 example matrices are the right size to show this on, because an 8 × 8 patch of C is precisely what one thread of kernel 5 owns: Boehm's TM and TN are both 8, and his BK is 8, so with K = 8 the inner loop you will see is his inner loop, unchanged. Watch what the thread needs for a single step of k, first with kernel 4's strip and then with the square.

Count it again, because it is the whole kernel. The patch has 64 outputs. Output (i, j) needs A value number i and B value number j. Every one of the 8 A values pairs with every one of the 8 B values, and each pairing is exactly one of the 64 outputs. So 16 loads produce 64 multiply-adds: 0.25 loads per FMA, which is the supply line chapter 7 drew.

9.2The outer product

The 8 × 8 grid of products you get by pairing every element of one vector with every element of another is called an outer product. It is the opposite of the dot product from chapter 1, which pairs elements position by position and sums them into one number. An outer product takes eight numbers and eight numbers and returns sixty-four, with no summing at all. The summing comes from repeating it: the outer product at step k is added into the same 64 accumulators as the outer product at step k − 1, and after the last step the accumulators hold the patch of C. Here it is with real numbers.

The one picture

Every value on the left is used eight times, and so is every value on top. That is where the whole speedup of kernels 4 and 5 comes from: a loaded number, once it sits in a register, is free to reuse, and the outer product is the arrangement that reuses each one as many times as the patch is wide.

9.3Kernel 5, every step

Now the kernel itself. Here is Boehm's inner loop, lightly trimmed. Each step of k has three phases: copy the eight A operands out of shared memory into registers, copy the eight B operands, and then do the sixty-four multiply-adds without touching memory at all.

float threadResults[TM * TN] = {0.0};   // 64 accumulators, in registers
float regM[TM] = {0.0};                 // 8 A operands, in registers
float regN[TN] = {0.0};                 // 8 B operands, in registers

for (uint dotIdx = 0; dotIdx < BK; ++dotIdx) {
  // phase 1: stage this thread's 8 A values (one column of As)
  for (uint i = 0; i < TM; ++i)
    regM[i] = As[(threadRow * TM + i) * BK + dotIdx];
  // phase 2: stage its 8 B values (one row of Bs)
  for (uint i = 0; i < TN; ++i)
    regN[i] = Bs[dotIdx * BN + threadCol * TN + i];
  // phase 3: 64 multiply-adds that touch no memory at all
  for (uint m = 0; m < TM; ++m)
    for (uint n = 0; n < TN; ++n)
      threadResults[m * TN + n] += regM[m] * regN[n];
}

Read it with the miniature's numbers. With the tile edge set to 8, the thread's patch is the whole tile, so the block is this one thread (the real block has 256 of them, side by side). At dotIdx = d it copies column d of As into regM and row d of Bs into regN, sixteen loads, and then adds regM[m] × regN[n] into accumulator (m, n) for every m and n: sixty-four multiply-adds from registers alone. The animation runs all eight values of d, with the line of the kernel being executed marked as it goes, and checks the sixty-four accumulators against the full product at the end.

That staging step is what people mean when they say a kernel "caches in registers". Shared memory was a cache we filled by hand for the block; the register file is now a second cache we fill by hand for the thread. Each kernel in this book has added one more level of the hierarchy to the scheme, and this is the last level there is. There is nothing closer to the arithmetic than a register.

9.4From the miniature to the real block

With 64 outputs per thread the block has to change shape, for the same reason it did in kernel 4. Boehm's kernel 5 uses a 128 × 128 tile of C and keeps BK = 8. At 64 outputs per thread that is 256 patches of 8 × 8, one per thread; the As chunk is 128 × 8 = 1,024 floats and the Bs chunk 8 × 128 = 1,024, so each thread copies four elements of A and four of B per chunk, not one. The miniature's single thread had to copy the whole chunk itself; that, and the number of chunks, is the only place the two differ.

Two things changed at once here, and it is worth keeping them apart. The wider block tile cut the global-memory traffic, from K/32 reads per output to K/64, the same lever kernels 3 and 4 pulled. The square thread tile cut the shared-memory traffic, from 1.125 loads per FMA to 0.25, which is the lever chapter 7 said mattered now. Kernel 5 pulls both, and it needs at least 64 + 8 + 8 = 80 registers per thread to do it, since the accumulators have to live in registers for the whole kernel. That cost is the subject of the next chapter.

9.5Kernels 3, 4 and 5 are one idea, three times

Stepping back, the three shared-memory kernels are a single idea applied with increasing appetite: keep the operands close, and make each one you fetched serve as many multiply-adds as possible. The chart below is the whole story of them. Loads per multiply-add fall 2 → 1.125 → 0.25, and speed rises 2,980 → 8,475 → 15,972 GFLOP/s. They are mirror images, which is the point. Over this stretch, performance is set almost entirely by how many shared-memory instructions each unit of arithmetic costs.

Measured: 8,475 → 15,972 GFLOP/s, and we are past two thirds of cuBLAS with a kernel that is still only about forty lines long. Which raises the obvious question. If a bigger thread tile keeps helping, why stop at 8 × 8? Why not 16 × 16, with 256 accumulators? The answer is that registers are a shared, fixed resource on the SM, and the packing game that decides how many warps can be resident is the next chapter.
