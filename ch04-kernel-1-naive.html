Chapter 4 · The memory-starved kernels

Kernel 1: the naive version

One thread per output, a loop over k, and 1.3% of the machine. Before we make anything faster, we watch exactly where the first kernel's time goes.

Kernel · sgemm_naive · 309 GFLOP/s · 1.3% of cuBLAS · measured by Simon Boehm on an NVIDIA A6000

The obvious way to multiply two matrices on a GPU is to give every output element its own thread and let that thread compute the dot product it needs. That is kernel 1. It's worth reading in full, because every kernel in this book is a rewrite of these nine lines.

// one thread per output element
const uint x = blockIdx.x * blockDim.x + threadIdx.x;   // row of C
const uint y = blockIdx.y * blockDim.y + threadIdx.y;   // column of C

float tmp = 0.0;
for (int k = 0; k < K; ++k)
    tmp += A[x * K + k] * B[k * N + y];   // 2 loads, 2 FLOPs
C[x * N + y] = tmp;

It is correct, and it reaches 309 GFLOP/s on the A6000. That is 1.3% of what cuBLAS gets on the same problem, and about 1% of what the hardware can do. The rest of this chapter is about why, and the answer has nothing to do with the arithmetic. We'll first watch what one thread does, then what 32 of them do together, and then what the memory system has to do to keep them fed.

4.1One thread, one output

Follow one thread. The one in the animation owns C[2][5], so it needs all of row 2 of A and all of column 5 of B. Each pass through the loop loads one value from each, multiplies them, and adds the product into tmp. That variable lives in a register, a private slot inside the thread that costs nothing to read or write. After the last pass, tmp is the answer and gets written to C. (The matrices here are 8 × 8 so you can check the arithmetic by eye; the real ones are 4,092 × 4,092, and the loop runs 4,092 times instead of 8.)

Notice the ratio inside the loop. Every iteration issues two loads and does two floating-point operations, a multiply and an add. (The hardware fuses those into one instruction, a fused multiply-add or FMA, but it counts as two FLOPs.) Two loads for two FLOPs. Keep that ratio in mind; most of this book is about pushing it down.

4.2Threads come in warps

The hardware never runs a thread on its own. It runs threads in groups of 32 called warps, and the 32 threads of a warp execute the same instruction at the same moment, each on its own data. When a warp reaches the load A[x * K + k], it does not issue one address. It issues 32 addresses at once, as a single request. So to understand what a load costs, stop thinking about the thread and think about the warp: which 32 addresses go out together?

That depends on how threads are assigned to outputs. Inside a block, threads are numbered so that threadIdx.x changes fastest: threads 0 to 31 are the first warp, 32 to 63 the second, and so on. Kernel 1 uses threadIdx.x for x, which is the row index. So the 32 threads of a warp own 32 consecutive rows of C, all in the same column.

At k = 0, then, the warp's request for A reads: give me A[0][0], A[1][0], A[2][0], and so on down to A[31][0]. A column. Its request for B reads: give me B[0][0], thirty-two times over. Whether that is cheap or ruinous depends on one thing we haven't looked at yet, which is how those addresses sit in memory.

4.3What memory has to deliver

Memory is one long line of bytes, and a matrix has to be flattened onto it somehow. C and CUDA use row-major order: all of row 0, then all of row 1, and so on. Two neighbors in the same row are 4 bytes apart (one float). Two neighbors in the same column are a whole row apart, which for A is 4,092 floats, or 16,368 bytes.

And memory doesn't hand out individual floats. The smallest thing the memory system moves is a 32-byte sector: eight floats that sit side by side. Ask for one float and the whole sector it lives in comes back, whether you wanted the other seven or not. This is not a quirk to work around; it is how DRAM and the caches are built, and it's the single fact that makes kernel 1 slow.

So the warp's column request touches 32 different sectors, one per row, and 1,024 bytes come back to satisfy 128 bytes of demand. The B request is cheap by comparison: all 32 threads want the same element, so the hardware fetches its sector once and broadcasts the value to every thread. The bill for one k-step of one warp is 1,056 bytes moved for 64 FLOPs (32 threads, one multiply and one add each).

That last cell is the whole diagnosis in one number. The A6000 can move 768 GB per second and compute 30 trillion FLOPs per second, so it can afford roughly 0.026 bytes of memory traffic per FLOP if the arithmetic units are to stay busy. Kernel 1 demands 16.5. It is asking for six hundred times more bytes per operation than the machine can supply, and so the arithmetic units sit idle waiting for them. The L2 cache absorbs a lot of the repeated reads, which is why the kernel manages 309 GFLOP/s rather than something far worse, but caches soften the penalty; they don't remove it. Boehm's profiler reports the same thing from the other side: about 15 GB/s of useful memory throughput on a part that can do 768, and warps stalled on loads nearly all of the time.
